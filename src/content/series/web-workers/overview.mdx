You click "Import". Choose a large CSV. The button stays pressed. The cursor keeps spinning. The loading state you wrote — the one that was definitely supposed to appear — never gets a chance to render.

Nothing crashed. No error in the console. The browser tab is right there, technically alive. But the interface has stopped responding, because the only thread that can update it is buried inside a `for` loop parsing five thousand rows.

That is the problem. Not some edge case. Not a contrived benchmark. A real user action, on real data, producing a broken-feeling UI in a perfectly functional application.

This series starts from that freeze, explains precisely why it happens, and then fixes the app one architectural decision at a time — using a single demo codebase called **TaskFlow** that evolves across every post.

## Before We Go Deep, Here's the Smallest Possible Win

Theory without a payoff is hard to care about. Before the event loop, before worker types, before anything else — here is the simplest thing a Web Worker can do:

```js
// main.js
const worker = new Worker(new URL('./echo-worker.js', import.meta.url), {
  type: 'module',
});

worker.onmessage = (event) => {
  console.log(event.data); // "Hello from worker: world"
};

worker.postMessage('world');
```

```js
// echo-worker.js
self.onmessage = (event) => {
  self.postMessage(`Hello from worker: ${event.data}`);
};
```

Two files. One message out, one message back. The main thread stays free the entire time.

The rest of the series is the long answer to four questions that naturally follow from those fourteen lines:

1. Why does the main thread freeze in the first place?
2. What exactly happens when data crosses a worker boundary?
3. When is a worker worth the added complexity?
4. Which worker-shaped tool fits which real-world problem?

<Callout type="tip" title="What this first win is actually doing">
  It is not trying to teach the full API. It is there to make one thing emotionally real before the theory begins: work that leaves the main thread stops competing with your UI. Every post after this is a more precise version of that same idea.
</Callout>

## The Four Worker Types You Need to Keep Straight

The browser ships four tools that use the word "worker" or live conceptually nearby. They do not solve the same problem.

<Comparison
  headers={['Type', 'Best For', 'Scope', 'Keeps Shared State?', 'The Trap']}
  rows={[
    ['Dedicated Worker', 'CPU-heavy work for one page', 'One tab only', 'No — each page gets its own instance', 'The right default for most app offloading'],
    ['SharedWorker', 'One worker shared across tabs', 'Same-origin tabs', 'Yes — one shared execution context', 'Browser support is narrower than Dedicated'],
    ['BroadcastChannel', 'Cross-tab signals', 'Same-origin contexts', 'No — messaging only', 'Not a compute tool; sends events, not threads'],
    ['Service Worker', 'Network caching and request interception', 'URL scope', 'Not this kind of state', 'Frequently confused with Web Workers; completely different job'],
  ]}
  caption="The series starts with Dedicated Workers because that is where almost every real frontend performance problem begins."
/>

The last row deserves a sentence. Service Workers intercept network requests. Web Workers offload CPU work. Both sit in a separate thread; neither can access the DOM. But they solve fundamentally different problems, and treating them as interchangeable is the most common confusion this series is designed to permanently fix.

## The Demo App: TaskFlow

Every post in this series uses the same codebase. Not a collection of isolated demos — one real app that gets progressively less broken.

**TaskFlow** is a lightweight project management dashboard with three panels:

1. **Import panel** — accepts a CSV export from Jira or Linear. With a 5,000-task file, parsing freezes the UI for 300–500ms. This is the first thing we fix.
2. **Gantt panel** — a canvas-rendered chart for the current sprint. Computing task positions and painting the result drops frames noticeably on larger projects.
3. **Activity feed** — shows unread updates from teammates. Clicking "Mark all read" in one tab should sync to every other open tab. In `main`, it does not.

## Seven Terms That Appear Everywhere

These words repeat across every post. The overview defines them once so every post after this can move faster.

**`main thread`** — the browser thread that runs your JavaScript, processes user input, and coordinates rendering. There is only one. When it is busy, everything waits.

**`long task`** — any main-thread task that runs for more than 50ms. This is the threshold where jank becomes measurable and visible. The Lighthouse metric that captures it is Total Blocking Time.

**`clone`** — when data crosses a worker boundary, the default behaviour is a structured clone: the value is serialised and a new copy is created on the receiving side. Both sides own independent copies.

**`transfer`** — an alternative to cloning where ownership of the underlying buffer moves to the receiving context. The sending side can no longer access it. Transfer is zero-copy — no allocation, no serialisation cost.

**`shared memory`** — a `SharedArrayBuffer` that two threads can read and write simultaneously, with no copy at all. Fast, but requires careful coordination — otherwise two threads clobber each other's writes.

**`port`** — a message endpoint. `SharedWorker` and `MessageChannel` both use ports to route messages between specific senders and receivers. A port is a connection, not a value.

**`cross-origin isolation`** — the deployment configuration (`COOP`/`COEP` headers) that browsers require before they will hand out a `SharedArrayBuffer`. Without it, the API is disabled, full stop. Post 4.1 covers the headers and why they exist.

<InterviewLens>
  <LensQ q="What problem are Web Workers actually solving?">
    They solve a **main-thread scheduling problem**. The browser UI becomes unresponsive when expensive CPU work runs on the same thread that needs to respond to input and paint frames. A strong answer starts with user experience and frame budgets — not with API names. The API is only interesting once the problem is visible.
  </LensQ>

  <LensQ q="How would you decide whether a worker is worth introducing?">
    Measure first. Find the long task, confirm the work is CPU-bound rather than I/O-bound, and ask whether moving it off-thread will produce a meaningfully better experience than the message-passing overhead costs. Workers are a tradeoff, not a default upgrade. The answer is always "it depends" — but a good engineer can explain exactly what it depends on.
  </LensQ>

  <LensQ q="What is the difference between a Web Worker and a Service Worker?">
    A Web Worker is a compute offload tool — it runs your JavaScript on a separate thread to keep the main thread free. A Service Worker is a network proxy — it intercepts requests, manages a cache, and enables offline behaviour. If an answer conflates them because both contain the word "worker", it is missing the architectural distinction that this entire series is designed to make permanent.
  </LensQ>
</InterviewLens>
